# 프로젝트 중심 대시보드 구현 계획

작성일: 2026-10-05

## 목표

상단 프로젝트 선택을 모든 관제 화면의 공통 조회 범위로 사용한다. 화면 안에서는 인스턴스·환경·시간으로 범위를 좁힌다. 종합현황에서 문제를 확인한 뒤 같은 프로젝트와 인스턴스의 XLog·실시간 로그로 이동할 수 있게 구성한다.

2026-10-06 구현: 상단 프로젝트 선택, 독립 XLog·실시간 로그 메뉴, 프로젝트·인스턴스 범위의 XLog 요약과 산점도, 요청 정보 모달을 추가했다. 적용 방법과 해석 기준은 [프로젝트 관제와 실시간 로그 적용 가이드](project-dashboard-and-log-guide.md)를 참조한다.

## 현재 상태

- 중앙 Agent와 Collector는 HTTP 조회와 요청 기반 웹소켓 연결을 지원한다.
- 운영 중앙 Agent와 대상 Collector의 웹소켓 연결 성공을 사용자가 확인했다. 부하·장기 연결·전체 장애 시나리오를 통과했다는 의미는 아니다.
- 프로젝트 선택은 URL·세션 저장소와 동기화하며 다른 메뉴와 공유한다.
- XLog와 실시간 로그는 독립 메뉴와 기존 인스턴스 상세 화면에서 조회한다.
- XLog는 웹 요청의 경로·처리 시간·HTTP 결과 요약이다. SQL·메서드 추적은 제공하지 않는다.
- 로그 조회 사용 여부·조회 주기·파일 등록 기능과 메뉴·프로젝트 권한 체계가 존재한다.

## 화면 구성

```text
상단: [프로젝트 ▼]                              [사용자 ▼]
      프로젝트 검색 및 선택

메뉴
  종합현황
  프로젝트 / 인스턴스
  API 모니터링
  XLog
  실시간 로그
  인증서 관리
  설정

종합현황 내부: [인스턴스 ▼] [시간 범위 ▼]
             CPU | RAM | XLog
             JVM Heap | 디스크
```

프로젝트별 GNB를 추가하지 않는다. 프로젝트가 늘어나도 같은 메뉴를 유지하고 상단 선택으로 조회 대상을 바꾼다. 기존 보라색 강조색, 라이트·다크 테마, 공통 드롭다운·버튼·모달·전환 효과를 재사용한다.

### 상단 프로젝트 선택

- 종합현황 기본은 조회 가능한 첫 프로젝트와 첫 인스턴스다. 권한이 있는 프로젝트만 목록에 표시한다.
- 프로젝트명은 선택기에 표시하고 펼친 목록에서 이름·ID를 검색한다. CMS 사이트 선택기와 같은 160px·24px 크기를 사용한다. 다른 목록 화면의 전체 프로젝트 조회는 유지한다.
- 선택 결과는 메뉴 이동·새로고침에도 유지한다. URL에 조회 범위를 명시하고 세션 저장소에는 마지막 선택만 기억한다.
- URL의 명시적 프로젝트를 우선한다. 기존 `/projects/:projectId/instances/:instanceId` 상세 링크는 그 경로의 프로젝트를 우선한다.
- 프로젝트 변경 시 이전 인스턴스 선택·페이지 번호·로그 파일 선택을 초기화한다. 시간 범위는 유효한 값이면 유지한다.
- 삭제·권한 변경으로 선택 대상에 접근할 수 없으면 유효한 범위로 돌아가고 안내한다. 다른 프로젝트의 캐시 데이터를 잠시 표시하지 않는다.
- 사용자·메뉴·권한 등 전역 설정은 프로젝트 선택으로 데이터가 필터링되지 않는다. 프로젝트·인스턴스·임계치 등 프로젝트 관련 설정에는 선택 범위를 적용한다.

### 종합현황

| 범위 | 표시 내용 |
| --- | --- |
| 최초 진입 | 첫 프로젝트·인스턴스를 선택하고 해당 서버 한 대의 차트 표시 |
| 프로젝트 변경 | 이전 인스턴스 선택 해제 후 새 프로젝트의 첫 인스턴스 표시 |
| 인스턴스 변경 | 선택 서버의 자원·점검·연결 상태와 XLog 카드 표시 |

- 서버 수·API 이상·인증서 이상 숫자, 차트, 목록, 확인 항목이 모두 같은 범위를 따른다.
- 숫자를 클릭하면 현재 프로젝트·인스턴스 범위를 유지한 관련 화면으로 이동한다.
- 차트는 상단에 두고 목록과 확인 항목은 같은 행을 나누어 사용한다. 좁은 화면에서는 세로 배치한다.
- CPU·RAM·JVM Heap·웹앱 디스크·첨부파일 디스크처럼 간결한 제목을 사용한다. 중복 제목·브레드크럼·자동 갱신 주기 설명을 추가하지 않는다.
- 인스턴스명·ID·호스트·환경으로 검색한다. 통신 단절과 내부 점검·API·인증서 이상을 구분한다.

### 종합현황의 XLog 요약

- XLog는 CPU·RAM 등과 같은 그리드의 차트 카드로 표시한다. 별도 전체 폭 요약 섹션을 만들지 않는다. 선택 인스턴스의 수집 요청·HTTP 오류·평균·P95와 최근 1시간 산점도를 표시하고 점 크기는 2px로 사용한다.
- 상세 분석은 XLog 메뉴로 이동한다. 종합현황에 전체 요청 목록이나 로그 원문을 넣지 않는다.
- 종합현황에서는 선택 인스턴스 한 대만 조회한다. 전체 프로젝트 비교는 종합현황에 표시하지 않는다.
- 미사용, 웹소켓 미연결, 아직 수집된 요청 없음, 일부 데이터 누락을 구분한다. 미수집을 요청 0건 또는 정상 상태로 오해하게 표시하지 않는다.
- 현재 XLog는 버퍼·전송 한도와 보관 개수 상한이 있으므로 실제 전체 트래픽 건수나 완전한 TPS라고 표시하지 않는다. 요약은 선택 기간에 남아 있는 수집 데이터 기준이다.
- 오류는 수집된 HTTP 4xx·5xx로 분류하되 업무 오류와 같은 의미라고 단정하지 않는다. 응답시간 집계는 수집 데이터 기준 평균·P95와 대상 건수를 함께 제공한다.
- 제외 건수는 현재 연결에서 관측 가능한 범위만 표시한다. 현재 구현에 없는 과거 제외 건수 이력을 만들어 표시하지 않는다.

### XLog 메뉴

- `/xlog`에 독립 메뉴를 추가한다. 프로젝트·인스턴스·시간 범위·HTTP 결과·경로로 조회한다.
- 전체 프로젝트 선택 상태에서는 권한 내 프로젝트·인스턴스의 중앙 저장 데이터를 조회할 수 있다. 각 항목에 출처를 명시한다.
- 시간축과 처리 시간축의 분포 차트, 요청 목록, 선택 요청의 시각·메서드·경로·처리 시간·HTTP 상태를 표시한다.
- 프로젝트의 XLog 사용 설정과 인스턴스의 웹소켓 연결 상태를 구분한다. HTTP 모드에서도 이미 저장된 이력은 조회할 수 있지만 새 XLog 수집은 웹소켓 연결이 필요하다.
- 설정 변경·연결 시작은 변경 권한이 있을 때만 가능하다. 화면 진입·필터 변경으로 XLog를 켜거나 웹소켓 연결을 시작하지 않는다.
- 기존 인스턴스 상세 XLog 링크도 유지하고 같은 조회 컴포넌트를 재사용한다.

### 실시간 로그 메뉴

- `/logs`에 독립 메뉴를 추가한다. 상단 프로젝트 범위 내에서 인스턴스 한 개와 등록된 로그 파일 한 개를 선택한다.
- 전체 프로젝트 선택 상태라면 먼저 프로젝트와 인스턴스를 선택한다. 모든 대상 WAS의 로그를 한꺼번에 조회하지 않는다.
- 조회 시작·일시정지·조회 주기·최근 조회 결과·파일 회전/잘림 안내를 제공한다. 기존 `LogPanel`의 파일 등록·사용 여부·조회 주기·커서 읽기를 재사용한다.
- 화면 진입만으로 파일을 읽지 않는다. 사용자가 조회 시작을 누를 때만 추가 구간을 읽는다. 로그 파일 목록·설정 조회와 실제 파일 읽기는 구분한다.
- 메뉴 이탈, 프로젝트·인스턴스·파일 변경, 브라우저 탭 숨김 시 조회를 멈추고 타이머·진행 중 요청을 정리한다. 돌아왔을 때 조회를 자동 재개하지 않는다.
- HTTP 모드는 기존 로그 API, 웹소켓 모드는 기존 연결의 명령을 사용한다. 로그 조회 때문에 연결을 새로 시작하거나 재시도하지 않는다.
- 로그 원문 접근은 기존 제한을 유지한다. 조회 권한이 있는 사용자가 모두 원문을 볼 수 있도록 권한을 넓히지 않는다.
- 현재 웹소켓 조회 로그는 중앙 저장 이력으로 남는다. 화면 버퍼와 저장 이력을 구분하고 기존 용량·보관 정책을 유지한다. 이 UI 개편으로 전체 파일 지속 수집을 추가하지 않는다.

## 기술 적용

### 프런트엔드

1. `App.tsx` 상단에 공통 프로젝트 선택을 배치한다. 프로젝트 범위·유효성 검사·URL 동기화를 공통 상태로 관리한다.
2. `DashboardPage.tsx`의 페이지 내부 프로젝트 상태를 공통 범위로 교체한다. API·인증서·인스턴스 목록의 개별 필터도 같은 범위로 연결한다.
3. `/xlog`, `/logs` 경로와 메뉴를 추가하고 `menuForPath`, 메뉴 제목·선택 표시·이동 링크를 갱신한다.
4. `CollectorEvents`와 `LogPanel`을 재사용한다. 현재 인스턴스 상세에서 사용하는 기능도 유지한다.
5. React Query 키에 프로젝트·인스턴스·시간·필터를 포함한다. 범위 변경 뒤 도착한 이전 요청 결과와 이전 로그 버퍼가 새 화면에 섞이지 않게 한다.

### 중앙 Agent API와 DB

1. 기존 종합현황 API에 프로젝트·인스턴스 선택 조건을 추가하거나 기존 조건을 확장한다. 차트뿐 아니라 요약과 확인 항목까지 같은 서버 측 조건으로 집계한다.
2. 기존 Collector 이벤트 조회 API에 기간·HTTP 결과·경로 조건을 확장하고 페이지 크기에 상한을 둔다. 프로젝트 전체 조회와 요약 API는 인스턴스별 반복 호출 대신 DB에서 조회·집계한다.
3. XLog 집계는 중앙 `collector_events`에서 수행한다. 종합현황 조회 때문에 대상 서버를 호출하지 않는다.
4. 화면 검색을 위한 이벤트 시간 필드를 정한다. 요청 시각과 중앙 수신 시각을 혼동하지 않고 필터·차트·요약에서 동일한 기준을 사용한다. 현재 JSON 필드와 인덱스로 먼저 검증하고 필요한 인덱스만 새 Flyway 마이그레이션으로 추가한다.
5. XLog·실시간 로그 메뉴를 메뉴 관리에 등록하고 기존 역할·프로젝트 접근 검사를 API에도 적용한다. 새 메뉴 권한은 기존 기능 접근 수준을 보존하도록 매핑하며 무조건 전체 허용하지 않는다.
6. `contracts/center-api.openapi.yaml` 수정 후 생성 클라이언트를 다시 생성한다. 적용된 `V18`은 수정하지 않고 추가 변경이 필요하면 새 마이그레이션을 사용한다.

### 대상 Collector

화면 개편은 기존 Collector API·웹소켓 명령을 재사용한다. 날짜별 로그 파일 전환과 웹소켓 로그 오류 코드 개선을 함께 추가했으므로 해당 기능은 공통 Collector JAR 교체가 필요하다. 프로젝트별 Java 소스와 web.xml 변경은 필요하지 않다.

웹소켓 자동 시작·재연결, HTTP 자동 전환, XLog 기본 사용 정책은 변경하지 않는다. 공통 프로젝트 선택은 화면의 조회 범위이며 수집 설정 변경 명령이 아니다.

## 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 공통 프로젝트 선택·URL·권한 | 메뉴 이동·새로고침·상세 직접 진입에서 프로젝트 범위 일치 |
| 2 | 종합현황 범위 통일·인스턴스 검색 | 요약 숫자·차트·확인 항목·이동 링크가 같은 범위 표시 |
| 3 | 독립 XLog 메뉴·이벤트 검색 API | 프로젝트/인스턴스/기간별 요청 목록·차트 조회, 자동 수집 시작 없음 |
| 4 | 종합현황 XLog 집계 | 수집 데이터 기준 요약과 미사용·단절·미수집 상태 구분 |
| 5 | 독립 실시간 로그 메뉴 | 명시적 시작, 범위 변경·이탈 시 중단, 기존 파일·주기·권한 재사용 |
| 6 | 권한·테마·회귀 검증과 배포 안내 | 기존 HTTP·웹소켓 수집 유지, 두 테마·모바일·권한 검사 통과 |

1~2단계에서 프로젝트 중심 구조를 먼저 확정한 뒤 XLog와 로그를 추가한다. 진행 중에도 기존 인스턴스 상세 기능을 사용할 수 있게 유지한다.

## 검증 계획

- 프로젝트 A → B 전환 시 이전 카드·차트·요청 목록·로그 내용이 섞이지 않는지 확인한다.
- URL 직접 진입, 새로고침, 뒤로가기, 프로젝트 삭제·권한 회수 시 범위가 일관적인지 확인한다.
- 화면 진입·필터 변경만으로 연결 시작·XLog 사용 설정·로그 파일 읽기 API가 호출되지 않는지 검사한다.
- 로그 조회 중 프로젝트·인스턴스·파일 변경 및 메뉴 이탈 후 추가 파일 읽기가 멈추는지 확인한다.
- XLog 집계의 기간·오류·응답시간·빈 결과·보관 상한 영향을 가상 데이터로 검증한다. 수집 건수를 전체 요청량으로 표현하지 않는지도 확인한다.
- 조회자·운영자·관리자와 프로젝트별 권한으로 목록·집계·로그 원문·설정 변경의 API 접근을 검사한다.
- 기존 HTTP 조회, 웹소켓 연결 시작·종료, 단절 후 자동 재연결 금지와 로그 주기 설정이 유지되는지 검사한다.
- 관련 자동 테스트·타입 검사·API 생성 일치 검사·프런트엔드 빌드를 실행하고 라이트·다크·좁은 화면·키보드 동작을 확인한다.
- 대상 WAS 부하는 이전과 같은 수집 설정에서 비교한다. UI 개편만으로 대상 서버 부하가 줄었다거나 0이라고 주장하지 않는다.

## 반영 범위

중앙 Agent의 프런트엔드·API·메뉴 및 필요한 DB 마이그레이션이 주 반영 대상이다. 배포 전 운영 DB와 설정을 백업하고 `operations` 브랜치를 기준으로 중앙서버를 재빌드한다. 실제 고객 주소·토큰·로그·배포 파일은 Git에 포함하지 않는다.

공개용 문서에는 이 계획처럼 일반 기능과 가상 범위만 사용한다. 운영 저장소의 커밋 이력을 공개 저장소로 옮기지 않는다.
