# Hermes 엔터프라이즈 운영 개선 및 실시간 로그 작업 지시서

2026-10-05 구현 반영: 실시간 로그의 초기 폴링 기능을 추가했습니다. 로그별 사용/미사용, 조회 주기(5~1,800초), 경로·인코딩 설정과 화면을 보는 동안만 읽는 동작을 지원합니다. 현재 사용자의 요청에 따라 로그 원문을 마스킹하지 않으며 중앙에 본문을 저장하지 않습니다. 이 문서의 마스킹 권고는 현재 구현에 적용하지 않습니다. 운영 사용에는 새 에이전트 JAR와 허용 폴더 설정 반영이 필요합니다. 구체적인 동작·반영 안내는 [실시간 로그](realtime-logs.md)에 정리했습니다.

작성일: 2026-10-04

## 1. 목적과 적용 범위

여러 운영자가 여러 프로젝트를 담당해도 장애 확인, 담당자 알림, 조치 기록, 권한 관리, 장기 조회와 복구를 수행할 수 있도록 Hermes를 개선한다.

샘플 프로젝트, 샘플 대학, 샘플 기업 등 모든 프로젝트에 공통으로 적용한다. 특정 프로젝트나 외부 서비스 업체에 종속된 화면·구조를 만들지 않는다. 기존 보라색·화이트 디자인과 데스크톱·모바일 사용성을 유지한다.

이 문서는 대화에서 합의한 개선 방향을 작업 지시 형태로 정리한 것이다. 아래의 미래 기능은 구현 완료를 의미하지 않는다. 설정 수치 중 명시적으로 '제안 기본값'이라고 표시한 것은 구현 및 부하 검증 과정에서 조정한다.

## 2. 현재 상태와 미구현 범위

- 기존 프로젝트·인스턴스 관리, 자원 수집, 내부 점검, API 점검, 인증서 점검을 기반으로 확장한다.
- 메인 및 서버 자원·DB Pool 차트의 조회 기간은 하루(24시간), 일주일(7일), 한 달(30일), 1년(365일)을 지원하도록 변경했다.
- 현재 이력 보관 기간은 366일이다. 이는 장기 집계 저장소를 완성한 상태가 아니다. 차트에 표시할 점을 줄이는 것과 DB에 저장하는 원본 양을 줄이는 것은 별개의 작업이다.
- 저장되기 전 또는 이미 삭제된 과거 기록은 복구하거나 임의의 값으로 채우지 않는다.
- 현재 서버용 Docker Compose 구성은 한 장비에서 대시보드, PostgreSQL, HTTPS 프록시를 함께 운영한다. 장비 장애 시 관제도 함께 중단될 수 있다.
- 아래의 장애 처리 체계, 담당자 알림, 세분화된 프로젝트 권한, 장기 집계, 실시간 로그 조회는 추가 작업 대상이다. 실제 코드에서 이미 지원하는 부분은 재사용하고 중복 구현하지 않는다.

## 3. 우선순위

| 순서 | 작업 | 기대 결과 |
| --- | --- | --- |
| 1 | 장애 상세 및 이력 | 발생 원인, 지속 시간, 복구 여부, 담당자와 조치 내역을 확인 |
| 2 | 담당자 알림 | 필요한 사람에게 알림을 보내고 중복·점검 알림을 줄임 |
| 3 | 사용자·프로젝트 권한 및 변경 이력 | 담당 범위만 접근하고 설정 변경자를 추적 |
| 4 | 장기 데이터 집계 및 백업·복구 | 1년 조회와 데이터 증가에 대응하고 장애 후 복구 |
| 5 | 수집 작업 격리 및 운영 안정성 | 느린 API가 다른 서버의 자원 수집을 지연시키지 않음 |
| 별도 단계 | 실시간 로그 조회 | 장애 조사 중 해당 운영 서버의 새 로그를 확인 |

실시간 로그는 초기 단계에서 파일 읽기 방식으로 구현한다. 중앙 로그 저장소 구축은 별도 확장 단계로 둔다.

## 4. 장애 상세 및 이력

### 필요한 정보

- 프로젝트, 인스턴스, 문제가 발생한 항목
- 서버 수집, CPU·RAM·JVM·디스크, 내부 점검, 외부 API, 인증서 등 문제 구분
- 발생 시각, 마지막 확인 시각, 복구 시각, 지속 시간
- 이해할 수 있는 원인 설명과 원래 결과 코드
- 담당자, 처리 상태, 조치 내용과 변경 이력

### 동작

- 동일 항목의 연속 실패는 하나의 진행 중 장애로 관리한다.
- 복구되면 해당 장애를 종료하고, 나중에 재발하면 새 장애로 기록한다.
- 서버 자원 수집 정상 여부와 외부 API 실패 여부를 분리해서 보여준다.
- 프로젝트 상태만 '장애'라고 표시해 서버가 내려간 것처럼 오해하게 만들지 않는다.
- 원인 코드가 없거나 확인되지 않은 경우 원인을 추측해서 확정하지 않는다.

예시 화면 내용:

> Instagram 게시물 조회 실패
> 서버 자원 수집: 정상
> 원인: 인증 토큰 만료 — 응답 결과로 확인된 경우에만 표시
> 발생: 14:20 / 지속: 12분
> 담당자: 홍길동 / 처리 상태: 확인 중

### 완료 기준

- 외부 API 실패만으로 서버 수집 중단이라고 표시하지 않는다.
- 장애 상세에서 발생·복구 및 조치 내역을 확인할 수 있다.
- 같은 실패를 반복 수집해도 장애 이력이 불필요하게 여러 건으로 생성되지 않는다.

## 5. 알림 정책

- 프로젝트별 담당자와 알림 수신 경로를 설정한다.
- 장애 발생과 복구 알림을 지원한다.
- 같은 장애의 반복 수집마다 새 알림을 보내지 않는다.
- 반복 알림 간격, 관련 장애 묶음, 점검 시간의 알림 일시 중지를 지원한다.
- 알림 전송 실패는 기록하고 제한된 방식으로 재시도한다. 알림 실패가 자원 수집을 막지 않도록 한다.
- 프로젝트 담당자가 바뀌어도 코드 수정 없이 설정으로 반영할 수 있게 한다.

참고: [Grafana 알림 그룹화](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/), [알림 일시 중지](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/create-silence/).

## 6. 사용자·프로젝트 권한 및 변경 이력

- 관리자, 운영자, 조회자 역할을 구분한다.
- 프로젝트별 조회·수정 권한을 서버 API에서 검사한다. 화면의 버튼 숨김만으로 제한하지 않는다.
- API 점검 실행, 사용 중지, 주기 변경, 임계치 변경, 인스턴스 설정 및 로그 조회 권한을 구분한다.
- 설정을 변경한 사용자, 시각, 대상, 변경 전후 값과 성공 여부를 기록한다.
- 토큰, 비밀번호, 인증 정보는 변경 이력과 API 응답에 원문으로 노출하지 않는다.
- 로그 본문 접근은 일반 자원 조회보다 민감할 수 있으므로 별도 권한을 고려한다.

## 7. 장기 데이터 집계

제안 보관 정책:

| 데이터 | 해상도 및 보관 방향 |
| --- | --- |
| 최근 30일 자원 기록 | 1분 단위 원본 |
| 최근 1년 자원 기록 | 시간 단위 평균·최대·최소 집계 |
| 장기 보고서 | 일 단위 집계, 보관 기간은 운영 요구에 맞춰 결정 |
| 장애·조치 이력 | 자원 원본과 별도로 보관 |

- 평균만 저장하지 않는다. CPU 급등 같은 순간적인 문제를 확인할 수 있도록 최대값도 보관한다.
- 프로젝트와 인스턴스, 디스크 경로·DB Pool별 구분을 유지한다.
- 웹앱과 첨부파일 경로가 같은 볼륨일 수 있으므로 단순 합산해 용량을 중복 계산하지 않는다.
- 조회 기간에 맞는 원본 또는 집계 데이터를 사용한다. 사용한 집계 기준을 툴팁 등 필요한 위치에서 설명한다.
- 미수집 구간을 0으로 만들지 않는다. 유효한 0과 미수집을 구분한다.
- 집계가 성공하기 전에 원본을 삭제하지 않는다. 집계 재실행 시 중복되지 않도록 한다.
- 먼저 현재 PostgreSQL 구조를 확장하는 방안을 검토하고, 실제 데이터량·조회 성능을 근거로 별도 시계열 저장소 도입 여부를 결정한다.

## 8. 수집 및 운영 안정성

- 자원 수집, 내부 점검, 외부 API 점검, 인증서 점검, 로그 조회의 실행 자원과 제한을 검토한다.
- 느린 외부 API나 로그 조회가 CPU·RAM 수집 작업을 밀어내지 않도록 제한된 실행 풀 또는 별도 작업 경로를 사용한다.
- 동시 실행, 대기열 크기, 요청 시간, 응답 크기, 재시도 횟수를 제한한다.
- 기존의 인스턴스별 실행 중복 방지와 보안 검증을 유지한다.
- 운영 서버별 부하와 중앙 서버의 작업 대기·실패·수집 지연을 관측할 수 있게 한다.
- 이중화하는 경우 여러 중앙 서버가 같은 점검을 중복 실행하지 않도록 작업 소유권을 관리한다.

### 배포·복구

- 지속 운영에는 전용 서버 구성을 권장한다.
- DB 자동 백업을 현재 장비 외부에 보관한다. 같은 장비의 Docker 볼륨만으로 백업을 대체하지 않는다.
- 백업 파일 생성 성공뿐 아니라 실제 복구 테스트를 수행한다.
- 복구 목표 시간과 허용 데이터 손실을 먼저 정하고, 그 기준에 따라 백업 주기와 이중화 범위를 정한다.
- 배포 후 상태 확인과 이전 버전으로 되돌리는 절차를 마련한다. DB 변경의 호환성도 확인한다.
- 별도의 외부 점검으로 Hermes 자체의 접속·수집 상태를 확인한다.
- 기존 백업·복구 스크립트가 있으면 현재 서버 Compose 구성에서도 동작하는지 검증하고 재사용한다.

## 9. 실시간 운영 로그: 초기 구현 방식

### 기본 구조

```text
운영 서버의 기존 로그 파일
          ↓ 허용된 파일의 끝부분 및 새로 추가된 부분만 읽기
프로젝트 에이전트
          ↓ 인증된 조회
Hermes 중앙 서버
          ↓ 권한 확인 후 전달
대시보드 로그 화면
```

- 브라우저가 운영 서버 에이전트에 직접 접속하지 않는다.
- 기존 로그 파일을 읽는다. 기존 Log4j 설정이나 로그 저장 경로를 변경할 필요는 없다.
- PostgreSQL에 운영 로그 본문 전체를 저장하지 않는다.
- DB에는 로그 조회 설정 및 사용자별 조회 이력을 저장한다. 로그 본문을 감사 기록이나 중앙 서버의 자체 로그에 남기지 않는다.

### 화면 동작

1. 로그 화면을 열면 최근 200줄을 먼저 보여준다. 파일 끝부분에서 제한된 양만 읽는다.
2. 이후 마지막으로 읽은 위치 이후에 추가된 로그만 조회해서 화면에 붙인다.
3. 실시간 모드는 제안 기본값 5초 간격의 폴링으로 구현한다. 즉시 스트리밍과 동일한 지연을 보장하는 기능은 아니다.
4. 일시정지·다시 시작, 자동 스크롤 켜기·끄기를 제공한다. 일시정지 시 대상 서버 조회도 중단한다.
5. 화면을 닫거나 다른 페이지로 이동하면 해당 구독을 종료한다. 다른 사용자가 보고 있지 않으면 대상 서버 조회도 중단한다.
6. 화면에 남기는 로그 수를 제한해 브라우저 메모리 증가를 막는다.
7. 파일 교체·축소가 발생하면 새 파일을 감지해 읽기 위치를 갱신하고, 교체 또는 누락 가능성을 화면에 알린다.

### 조회 제한과 부하 제어

제안 기본값:

| 항목 | 제한 |
| --- | --- |
| 최초 조회 | 최근 최대 200줄 |
| 대상 서버의 1회 읽기 및 응답 | 최대 256KB, 전체 파일 스캔 금지 |
| 새 로그 조회 간격 | 5초, 필요하면 10초로 조정 |
| 대상 서버 동시 로그 조회 | 서버별 최대 1건 |
| 파일 읽기·응답 시간 | 짧은 제한 적용, 구체적인 값은 운영 검증 후 확정 |
| 중앙 서버 공유 | 동일 파일의 수집 결과를 권한 있는 여러 사용자에게 공유 |

- 최초 200줄도 256KB 제한보다 우선하지 않는다. 긴 한 줄이나 큰 예외 로그 때문에 제한을 넘지 않도록 한다.
- 같은 파일을 여러 사람이 봐도 대상 서버의 요청 수가 사용자 수만큼 늘어나지 않도록 중앙에서 공유한다. 서로 다른 파일의 요청도 서버별 제한을 지킨다.
- 화면 갱신 때마다 파일 처음부터 읽거나 최근 200줄을 반복 전송하지 않는다.
- 전체 파일 검색, 압축 로그 해제, 무제한 다운로드는 기존 WAS 내부에서 실행하지 않는다.
- 읽기 제한을 초과한 새 로그가 있으면 한 번에 모두 가져오지 않는다. 다음 읽기 위치를 유지하며 제한된 속도로 이어 읽거나, 누락 정책과 표시를 명확히 한다.
- 타임아웃 또는 읽기 지연이 반복되면 자동 갱신을 멈추거나 간격을 늘린다. 재시도를 몰아서 실행하지 않는다.
- 비활성 사용자·탭 또는 연결이 끊긴 사용자의 구독은 정리한다.
- 중앙 서버의 임시 버퍼·캐시는 크기와 수명을 제한하고 DB 영구 저장으로 바꾸지 않는다.

### 파일 읽기 정확성

- 파일 식별 정보와 바이트 위치를 이용해 새 부분만 읽는다.
- 읽기 위치·파일 식별 정보는 클라이언트가 임의 파일 접근에 악용할 수 없도록 서버에서 검증한다.
- 파일 교체, 같은 이름의 새 파일, 파일 크기 감소를 구분한다. 이미 삭제된 이전 파일의 내용을 복원한다고 약속하지 않는다.
- UTF-8 등 문자 인코딩과 바이트 경계, 아직 완성되지 않은 줄, 긴 한 줄, 여러 줄 예외 로그를 처리한다.
- 화면에서 오래된 줄을 제거하는 것과 대상 파일의 읽기 위치를 건너뛰는 것은 구분한다.

### 보안 및 오류 처리

- 에이전트 설정에서 허용한 로그 ID·파일만 조회한다. 사용자가 임의의 파일 경로를 입력해 읽을 수 없게 한다.
- 경로 이동 및 심볼릭 링크 등을 통한 허용 범위 밖 접근을 차단한다.
- 프로젝트 권한과 별도 로그 조회 권한을 검사하고 기존 에이전트 인증을 유지한다.
- 토큰, 비밀번호, 인증 헤더 등 민감 정보를 응답 전에 가린다. 개인정보도 로그 유형에 맞춰 처리한다.
- 자동 마스킹이 모든 민감 정보를 제거한다고 보장하지 않는다. 노출 위험이 큰 로그는 조회 대상에서 제외하거나 추가 규칙을 적용한다.
- 로그를 HTML로 실행하지 않고 일반 텍스트로 표시한다.
- 읽기 권한 없음, 파일 없음, 응답 지연, 서버 연결 실패를 각각 구분해서 표시한다.
- 읽기 오류를 해결한다며 운영 로그 파일의 권한이나 기존 로깅 설정을 자동 변경하지 않는다.

### 부하에 대한 판단과 검증

파일 끝부분 또는 새로 추가된 제한된 데이터만 5~10초 간격으로 읽는 구성은 일반적으로 전체 파일 검색보다 부담이 작다. 다만 대상 서버에 장애가 생기지 않는다고 보장할 수는 없다. 디스크가 느리거나 CPU·메모리가 이미 고갈된 서버에서는 작은 요청도 영향을 줄 수 있다.

기존 WAS 안의 에이전트가 실행하는 파일 읽기는 WAS 자원을 일부 사용한다. 다음 조건에서 적용 전후를 비교한다.

- 일반적인 로그 발생량과 예외 로그가 급증하는 상황
- 큰 파일, 긴 한 줄, 파일 교체 및 파일 축소
- 여러 사용자의 같은 로그 조회와 서로 다른 로그 조회
- 느린 읽기·네트워크 단절·일시정지·화면 종료
- 대상 서버 CPU·메모리·디스크 I/O·서비스 응답시간
- 중앙 서버 동시 요청·응답 크기·버퍼 메모리와 기존 자원 수집 지연

운영 적용 전에 허용 가능한 영향 범위를 정하고 측정한다. 영향이 크면 읽기 양·주기를 줄이거나 실시간 조회를 중지한다.

### 초기 기능의 한계

- 대상 서버가 내려가면 실시간 파일 조회도 불가능하다.
- 삭제되거나 교체된 과거 로그를 항상 검색할 수 있는 기능이 아니다.
- 사용자가 화면을 보지 않는 동안 로그 본문을 중앙에 영구 수집하지 않는다.
- 5초 폴링은 대략 해당 주기와 요청 처리 시간만큼 표시 지연이 생긴다.

## 10. 중앙 로그 수집: 확장 단계

장애 전후의 과거 로그 보관, 여러 서버 통합 검색, 운영 서버가 내려간 후 로그 확인이 필요해지면 별도 중앙 수집 방식으로 확장한다.

- WAS와 별도로 실행되는 로그 수집기가 새 로그를 전용 저장소로 전송한다.
- 로그 본문은 별도 로그 저장소에 보관하고 대시보드는 해당 저장소를 조회한다.
- 수집기 CPU·메모리·읽기 속도·전송량·로컬 대기 버퍼를 제한한다.
- 전송 실패 시 무제한 재시도·버퍼 증가·디스크 점유가 발생하지 않게 한다.
- 로그 보관 기간, 프로젝트 접근 권한, 민감 정보 처리, 저장 비용을 별도로 설정한다.
- 중앙에 도착하지 못한 로그는 운영 서버 장애 후 조회할 수 없다는 한계를 명확히 한다.
- 제품·저장소 선정은 필요한 검색 범위와 실제 로그량을 확인한 후 진행한다. 현재 단계에서 특정 제품 도입을 확정하지 않는다.

## 11. 에이전트 작업 수칙 및 완료 기준

- 작업 전 관련 코드의 실제 수집·인증·조회 흐름과 프로젝트 지침을 읽는다.
- 기존 기능을 재사용하고 불필요한 의존성·공통 추상화를 추가하지 않는다.
- API 변경 시 계약 및 생성 클라이언트를 함께 반영한다.
- 공통 에이전트 JAR 변경 시 기존 프로젝트 호환성과 실제 대상 Java 버전을 확인한다.
- 프로젝트별 설정·배포 경로는 실제 운영 설정을 기준으로 검증한다. 샘플 대학에서 발생했던 클래스 경로 오류를 반복하지 않는다.
- 신규·수정 파일, 컴파일 대상·Java 버전, 운영 반영 경로와 설정 항목을 구분해 제공한다.
- 토큰·비밀번호·실제 로그 원문을 문서, 테스트 산출물 또는 Git에 넣지 않는다.
- 관련 자동 테스트와 실제 흐름 검증을 수행한다. 전체 파일 스캔 방지, 읽기 제한, 권한, 파일 교체와 폴링 중단을 특히 확인한다.
- 완료 보고에는 변경 내용, 검증 결과, 실제 배포 여부와 남은 제한을 명시한다.
- 이 문서는 작업 계획이며, 그 자체로 외부 알림 발송·운영 서버 변경·중앙 로그 제품 도입을 완료하거나 승인했다는 의미는 아니다. 실행 시 사용자 지시 및 세션에서 승인된 범위를 확인한다.

## 12. 에이전트에 전달할 시작 프롬프트

> `docs/enterprise-monitoring-plan.md`를 읽고 현재 코드와 운영 구조를 먼저 확인해라. 구현된 부분과 미구현 부분을 구분하고, 지정받은 단계에 필요한 변경만 진행해라. 기존 보안·에이전트 호환성을 유지하고 모든 프로젝트에 공통으로 적용해라. 실시간 로그는 허용된 파일의 제한된 끝부분과 새 데이터만 읽고, 운영 로그 본문을 PostgreSQL에 저장하지 마라. 관련 테스트 및 부하 검증을 수행하고 신규·수정 파일, 반영 경로, 검증 결과와 남은 제한을 보고해라.
